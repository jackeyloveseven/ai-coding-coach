Tiering

Every task gets tiered first: two questions decide how much to teach

How quietly does this fail if it's wrong? How much does doing it by hand build judgment? When unsure, it tiers yellow — better to under-teach than to interrupt somewhere it shouldn't.

Green: let go
boilerplate, argparse, logging, plotting, shell commands
Done well, no teaching. Learning API syntax or fighting matplotlib styling adds nothing; unsolicited lessons are just annoying.
Amber: read it
data pipelines, training loops, loss implementations, eval code, hyperparameter changes
Done, plus a Read-it checkpoint of six lines or fewer: what the key lines do, where this is most likely to be silently wrong, and a check you can run yourself.
Red: by hand
attention / loss / sampling / optimizers, design decisions, experiment design, reading a run, deciding next steps
Coach mode: scaffolding first, then you go, then we compare the differences. The decision stays yours throughout.

Motivation

Four failure modes

Writing code is depreciating fast. Judgment isn't. These are the four ways early-career ML engineers trip in the AI era — and everything in this repo points at one of them.

#1

It runs, but the result is quietly wrong

The most expensive bug isn't the one that throws. It's the one that runs, prints a metric, and is wrong. Train and eval reversed, the metric computed on augmented data, the loss accumulated without dividing by the right sample count — nothing crashes, it just sends you three months down a wrong conclusion.

The fix: the amber-tier silent risk is aimed at exactly this, with a check you can run yourself.

#2

The loss went down, but you don't know if it learned anything

The loss drops, the metric gains three points — is that the change working, or data leakage, or noise, or reward hacking? Deciding "how much counts as improvement" after seeing the result will almost always produce "it improved".

The fix: write the pre-registration (hypothesis / control / variable / criterion / stop-loss / prediction) before the run, and the criterion sits directly above the metric when you read it.

#3

The run finished and the next step is pure vibes

Continue or stop, which parameter to change, whether to add GPUs — nobody makes these calls for you. The AI doesn't know your business or your data either, so it can't give you a reliable answer.

The fix: the red tier withholds the answer and supplies scaffolding. You say what you intend to do next and why, then we compare.

#4

I've stopped doing the "judging" part

The agent writes nearly all the code and you review less and less. Judgment isn't taken from you by AI — it atrophies from disuse. And it doesn't lose value as AI gets better; it gains value as AI produces more.

The fix: a mastery ledger schedules reviews on a 1 / 3 / 7 / 16 / 35 day spacing, dropping a tier for topics that stabilized and raising one for topics you keep fumbling. To practice on purpose, run /coach-drill.

One line runs through all of it: the division of labor is not about who writes the code, it is about who is accountable for the result.

Resident cost

Two skills, split by who can trigger them

Both install, but the substance only loads when the situation calls for it. Run claude plugin details to see the exact numbers for your version.

skillTriggerWhat it doesResident
ai-coding-coach Automatic (model-invoked) Standing discipline. Active when you write code, debug, or read a log, pulling you into the judgment. description only
/coach-drill You type it (user-invoked) Explicit orchestration. Run it for a 15–25 minute session; it picks due topics from the ledger and drills them. description only

Only the two descriptions are resident. The substance — SKILL.md and the references/ files — loads on demand. So the standing cost is a couple of short descriptions, which is less than a typical CLAUDE.md rule or the description of one MCP server. /coach-drill's description stays in the skill list on purpose: disable-model-invocation turns off automatic triggering, not the description, so you still know the door is there.

Companion tooling

exptool: wiring the pre-registration into the training log

A discipline on its own does nothing. It has to show up in front of you at the right moment. exp reads the PLAN.md in the run directory and prints the criterion directly above the metrics.

$ exp status demo-sft
run:     demo-sft
machine: local
dir:     ./examples/demo-sft
method:  sft

health
  tmux train-demo: up
  log last updated: 2 minutes ago (train.log)

pre-registration
  criterion: judge by eval loss on the fixed dev set; must beat baseline by more than 0.02
  prediction: I expect eval loss 0.01-0.03 lower, confidence medium
  (full text: exp plan demo-sft)

progress
  step  4200/8000    loss 0.84    eval loss 0.91
  read the trend, not the step
CommandWhat it does
exp listWhich runs are registered, and which are still going
exp statusProgress, metric trend, health checks, plus the pre-registered criterion
exp planGenerates the six-item template when there's no PLAN.md; prints the full text when there is
exp reportRenders a self-contained HTML report: curves, criterion reference line, health checks

Every command prints the command it actually runs first (the grey + ssh ...). Copy it, modify it, use it directly — once you're comfortable you don't need the tool. It's a sanitized, generic build: hostnames, shared-disk paths and reward-service addresses all come from a config file, so it runs locally with no cluster.

Scope. This skill grew out of actual use rather than being designed up front. The tiering criteria are empirical, mastery levels rest on the coach's observation rather than an objective benchmark, and the current coverage leans toward training experiments in diffusion and RL post-training. Known limits are stated rather than hidden, because the whole skill is built on calibrated confidence — a product that oversells itself contradicts its own teaching.
